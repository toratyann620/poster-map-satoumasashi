# アプリ共通仕様

React Native (Expo) + NestJS + Next.js 構成で開発するアプリに共通する仕様・実装パターンをまとめたドキュメント。
別プロジェクトへの転用を意識して記述する。

---

## このドキュメントの使い方

> **このドキュメントは「守るべきルール集」ではなく「出発点」である。**

各アプリの実装にあたっては、このドキュメントの内容を参考にしつつも、そのアプリの目的・ユーザー・技術的制約を踏まえて自分で考え、**より良い実装があれば積極的に採用してよい**。

特に以下の点を意識すること:

- UX の観点から、このドキュメントの実装より優れた方法があれば迷わず採用する
- 採用したプロジェクトで実績が出た改善は、**このドキュメントに反映して全プロジェクトで共有する**
- 逆に、このドキュメント通りに実装したが問題が生じた場合も、原因と改善策をここに記録する

ドキュメントを「更新しない」ことが最大のリスクである。実装が変わったら必ずここを書き換えること。

## 0. 他の構成への読み替え（ポスターアプリでの実績）

本ドキュメントは Expo + NestJS + Next.js を前提に書かれているが、
**ポスターアプリ（React + Vite + Capacitor + Firebase）** に適用した際の対応表を残す。
同じ構成の案件はここを見れば読み替えられる。

| 仕様書の前提 | 読み替え先 | 補足 |
| --- | --- | --- |
| `SecureStore` | `localStorage` | RN に localStorage が無いための選択であって、機密だからではない。WebView 上では localStorage がそのまま使え、「その端末にだけ残る」性質も同じ。ただしプライベートモード等で例外を投げるため、読み書きは必ず try/catch で包む |
| `expo-secure-store` の JWT 保存 | Firebase Auth の永続化 | ネイティブでは `getAuth()` が使えず `initializeAuth(app, { persistence: indexedDBLocalPersistence })` が要る。`getAuth()` はブラウザ用のリダイレクト解決を組み込むため、`capacitor://` スキーム下で `onAuthStateChanged` が発火しない |
| `GET /app-version`（NestJS） | Firestore の `settings/appVersion` | エンドポイントを作らずドキュメント1件で済む。`onSnapshot` で購読すれば、リリース後に値を書き換えるだけで全端末に伝わる |
| `GET /notifications`（NestJS） | Firestore の `announcements` コレクション | 読み取りは承認済みメンバー全員、書き込みは管理者のみをセキュリティルールで縛る |
| `Application.nativeApplicationVersion` | `@capacitor/app` の `App.getInfo()` | |
| `expo-notifications` | `@capacitor/push-notifications` + FCM | APNs 認証キーを Firebase へ登録する作業が別途要る |

### 実装してみて分かったこと

- **本文をプレーンテキストとして描くこと。** お知らせの本文は改行を活かしたくなるが、
  そのために HTML として描くと注入の余地を作ることになる。CSS の `white-space: pre-wrap`
  で見た目だけ再現すれば足りる。
- **初期パスワードは画面を開いた時点で生成しておくと良い。** 入力欄を空にして
  「6文字以上」とだけ書くと、結局 `123456` のような値が入る。最初から生成済みの値を
  出し、作り直しボタンを添える方が確実だった。
- **`mustChangePassword` の解除には、セキュリティルール側の例外が要る。**
  ユーザー文書を管理者しか書けない設計にしている場合、本人がフラグを下ろせない。
  `affectedKeys().hasOnly(['mustChangePassword'])` と「false にすることだけ」の
  2条件で絞れば、権限昇格には使えない例外にできる。
- **アプリ内通知とお知らせは、UI を分けた方が壊れにくい。** ポスターアプリには
  すでに日付スワイプ付きの「デイリー通知」パネルがあり、そこへお知らせを相乗りさせると
  日付処理と絡んで壊しやすい。ベル（アプリ由来）とメガホン（人が書いた連絡）で
  アイコンごと分けた。
- **チュートリアルの1枚目には「スキップ」を置く。** 仕様書には無いが、全部見る気が
  無い人に5枚めくらせるより、すぐ本題に入れた方が良い。ドットも押せるようにして
  戻れるようにしてある。

## 1. チュートリアル

### 概要

初回ログイン後（ユーザーが初めてアプリを起動した際）に、アプリの主要機能をスライド形式で紹介するチュートリアルを表示する。

### 仕様

- スライド形式で機能一覧を紹介する（スライド数はアプリ機能に応じて調整）
- 横スクロール or ページネーション方式で「次へ」ボタンにより進める
- プログレスバー（ドットまたはバー）で現在位置を表示する
- 最終ページに「はじめる」ボタンを置き、タップでチュートリアルを閉じる
- 一度見せたら以降は表示しない（`SecureStore` でフラグ管理）
- ログアウト・再インストール後は再表示する（フラグがリセットされるため）

### 実装パターン (React Native / Expo)

```tsx
// apps/mobile/src/components/Tutorial.tsx
import { useState } from "react";
import { Animated, Modal, Pressable, View } from "react-native";
import * as SecureStore from "expo-secure-store";

const TUTORIAL_SHOWN_KEY = "tutorial_shown";

// 表示判定（ログイン後のホーム画面などで呼び出す）
const shown = await SecureStore.getItemAsync(TUTORIAL_SHOWN_KEY);
if (!shown) {
  setShowTutorial(true);
}

// 完了時
await SecureStore.setItemAsync(TUTORIAL_SHOWN_KEY, "1");
setShowTutorial(false);
```

```tsx
// アニメーション付きスライド（Animated.Value で横移動）
const slideAnim = useRef(new Animated.Value(0)).current;

const goNext = () => {
  Animated.timing(slideAnim, {
    toValue: -(step + 1) * SW, // SW = Dimensions.get("window").width
    duration: 300,
    easing: Easing.out(Easing.cubic),
    useNativeDriver: true,
  }).start(() => setStep((s) => s + 1));
};
```

### 各スライドの構成（推奨）

| 項目     | 内容                                    |
| -------- | --------------------------------------- |
| アイコン | 絵文字または SVG アイコン（大きめ表示） |
| タイトル | 機能名（短く）                          |
| 説明文   | 機能の概要（2〜3行程度）                |

## 2. 通知設定

### 概要

プッシュ通知・アプリ内通知（お知らせ一覧）・ポップアップ通知の 3 層で通知を提供する。

### 2.1 プッシュ通知

**モバイルアプリ側**

- `expo-notifications` を使用
- 起動時に `Notifications.requestPermissionsAsync()` でパーミッションを取得
- 取得した `ExpoPushToken` を API へ送信し、DBに保存する（`User.expoPushToken` フィールド）
- フォアグラウンド時は `Notifications.setNotificationHandler` で表示方法を制御

**API 側**

- Expo Push API (`https://exp.host/--/push/send`) へ POST するサービスを実装
- 環境変数 `PUSH_NOTIFICATIONS_ENABLED=true` を Cloud Run に設定しない限り実際には送信しない（開発中の誤送信防止）
- 管理画面から任意のタイミングで全員 or 特定ユーザーへ送信できる

**管理画面側**

- `/notifications` ページにタイトル・本文入力フォームと「送信」ボタンを配置
- 送信後は送信履歴としてDBに記録する

### 2.2 アプリ内通知一覧

- API: `GET /notifications` で通知一覧を取得
- 未読・既読判定: `SecureStore` に「最後に通知一覧を開いた日時」を保存し、それより新しい通知を未読とみなす
- ホーム画面のベルアイコンに未読バッジ（赤丸・件数）を表示

```ts
// 最終既読時刻を保存
await SecureStore.setItemAsync("notifications_last_read", new Date().toISOString());

// 未読件数の計算
const lastRead = await SecureStore.getItemAsync("notifications_last_read");
const unread = notifications.filter(
  (n) => !lastRead || new Date(n.createdAt) > new Date(lastRead)
).length;
```

### 2.3 ポップアップ通知

- 管理画面で通知に `isPopup: true` フラグを立てると、ユーザーがアプリを開いた際にモーダルで表示される
- 一度表示したポップアップは再表示しない（`SecureStore` に表示済み ID を保存）

```ts
const SHOWN_POPUPS_KEY = "shown_popup_ids";

// 表示済みIDリストを取得
const raw = await SecureStore.getItemAsync(SHOWN_POPUPS_KEY);
const shownIds: string[] = raw ? JSON.parse(raw) : [];

// 未表示のポップアップを抽出
const pending = popupNotifications.filter((n) => !shownIds.includes(n.id));

// 表示後に記録
await SecureStore.setItemAsync(
  SHOWN_POPUPS_KEY,
  JSON.stringify([...shownIds, popup.id])
);
```

## 3. アップデート通知

### 概要

アプリ起動時にサーバー側の最新バージョンと手元のバージョンを比較し、古い場合はアップデートを促すモーダルを表示する。

### 仕様

- API エンドポイント `GET /app-version` が現在の最新バージョン情報を返す
- アプリ起動時（ホーム画面マウント時）にバージョンチェックを実施
- バージョンが古い場合はモーダルを表示し、ストアへ誘導する
- `forceUpdate: true` の場合はモーダルを閉じられなくする（強制アップデート）
- `forceUpdate: false` の場合は「後で」ボタンで閉じられる。閉じた後は 7 日間再表示しない

### API レスポンス例

```json
{
  "ios": "1.3.0",
  "android": "1.3.0",
  "force_update": false
}
```

### モバイルアプリ実装

```ts
import * as Application from "expo-application";
import * as SecureStore from "expo-secure-store";

const SKIP_UPDATE_KEY = "skip_update_until";

// バージョン比較（semver ライブラリ推奨、なければ手動比較）
function isOutdated(current: string, latest: string): boolean {
  const c = current.split(".").map(Number);
  const l = latest.split(".").map(Number);
  for (let i = 0; i < 3; i++) {
    if ((c[i] ?? 0) < (l[i] ?? 0)) return true;
    if ((c[i] ?? 0) > (l[i] ?? 0)) return false;
  }
  return false;
}

// チェック処理
const data = await fetch(`${API_URL}/app-version`).then((r) => r.json());
const platform = Platform.OS === "ios" ? "ios" : "android";
const latestVersion = data[platform];
const currentVersion = Application.nativeApplicationVersion ?? "0.0.0";

if (isOutdated(currentVersion, latestVersion)) {
  if (!data.force_update) {
    // 7日間スキップ判定
    const skipUntil = await SecureStore.getItemAsync(SKIP_UPDATE_KEY);
    if (skipUntil && new Date() < new Date(skipUntil)) return;
  }
  setUpdateInfo({ latest: latestVersion, force: data.force_update });
  setShowUpdateModal(true);
}

// 「後で」タップ時
const skip = new Date();
skip.setDate(skip.getDate() + 7);
await SecureStore.setItemAsync(SKIP_UPDATE_KEY, skip.toISOString());
setShowUpdateModal(false);
```

### NestJS エンドポイント実装例

```ts
// app-version.controller.ts
@Get('app-version')
getAppVersion() {
  return {
    ios: process.env.APP_VERSION_IOS ?? '1.0.0',
    android: process.env.APP_VERSION_ANDROID ?? '1.0.0',
    force_update: process.env.APP_FORCE_UPDATE === 'true',
  };
}
```

環境変数 `APP_VERSION_IOS` / `APP_VERSION_ANDROID` を Cloud Run の環境変数で管理し、リリース時に更新する。

## 4. アプリのログイン情報

### 概要

ログイン情報（JWT トークン）をデバイスの安全なストレージに保存し、次回起動時に自動ログインを実現する。また、OSのパスワードマネージャーとの連携でユーザーの認証情報入力を補助する。

### 4.1 JWT の保存と自動ログイン

```ts
import * as SecureStore from "expo-secure-store";

const AUTH_TOKEN_KEY = "auth_token";

// ログイン成功時
await SecureStore.setItemAsync(AUTH_TOKEN_KEY, response.access_token);

// 起動時の自動ログイン確認
const token = await SecureStore.getItemAsync(AUTH_TOKEN_KEY);
if (token) {
  // トークン検証 → ホーム画面へ
}

// ログアウト時
await SecureStore.deleteItemAsync(AUTH_TOKEN_KEY);
```

### 4.2 TextInput の設定（パスワードマネージャー連携）

iOS / Android のネイティブパスワードマネージャー（iCloud キーチェーン、Google パスワードマネージャー等）に認証情報を保存・提案させるため、TextInput に適切なプロパティを設定する。

**ID・メールアドレス入力欄**

```tsx
<TextInput
  keyboardType="email-address"
  autoCapitalize="none"
  autoCorrect={false}
  textContentType="username"   // iOS: パスワードマネージャーとの対応付け
  autoComplete="username"      // Android: 同上
/>
```

**パスワード入力欄**

```tsx
<TextInput
  secureTextEntry
  autoCapitalize="none"
  autoCorrect={false}
  textContentType="password"        // 既存パスワードの自動入力を有効化
  autoComplete="current-password"   // Android 同上
/>
```

**初回パスワード設定欄（新規パスワード）**

```tsx
<TextInput
  secureTextEntry
  textContentType="newPassword"      // iOS: 強力なパスワードを提案
  autoComplete="new-password"        // Android 同上
  passwordRules="minlength: 6;"      // iOS: パスワードルールのヒント
/>
```

### 4.3 初期パスワード生成

管理者がユーザーを新規作成する際に発行する初期パスワードは、以下の要件を満たす乱数で生成する。

- 長さ: **6文字**（短すぎず、入力のしやすさを重視）
- 文字種: 英大文字・英小文字・数字の全てを含む
- 除外文字: `0`/`O`、`1`/`l`/`I` 等、見分けにくい文字は除外する
- ユーザーは初回ログイン後に必ずパスワードを変更する（`mustChangePassword` フラグで制御）

```ts
// packages/database/../credentials.util.ts
const UPPER_CHARS = 'ABCDEFGHJKLMNPQRSTUVWXYZ';  // O 除外
const LOWER_CHARS = 'abcdefghijkmnopqrstuvwxyz';  // l 除外
const DIGIT_CHARS = '23456789';                   // 0, 1 除外
const ALL_CHARS   = UPPER_CHARS + LOWER_CHARS + DIGIT_CHARS;
const LENGTH      = 6;

export function generateInitialPassword(): string {
  const chars = [
    randomFrom(UPPER_CHARS),
    randomFrom(LOWER_CHARS),
    randomFrom(DIGIT_CHARS),
  ];
  for (let i = chars.length; i < LENGTH; i++) {
    chars.push(randomFrom(ALL_CHARS));
  }
  // Fisher-Yates シャッフル
  for (let i = chars.length - 1; i > 0; i--) {
    const j = randomInt(i + 1);
    [chars[i], chars[j]] = [chars[j], chars[i]];
  }
  return chars.join('');
}
```

## 5. テスターとの連携

### 概要

アプリのテストは専任テスターが実施し、不具合・改善要望を Google スプレッドシートで管理する。開発者は発見された問題をスプレッドシートで確認し、修正後にステータスを更新する。

### 5.1 管理スプレッドシート

**URL**: https://docs.google.com/spreadsheets/d/1YfWo9xvDaRscJ3kHET-LUNd-SV1yvKilEeP5ZZO-Szc/edit

各プロジェクトごとにシートが分かれている。

| シート  | プロジェクト                           |
| ------- | -------------------------------------- |
| シート1 | 名簿クレンジングアプリ                 |
| シート2 | 党員アプリ（自民党アプリ）             |
| シート3 | ポスターアプリ                         |
| シート4 | 凡例（記入者・優先度・ステータス一覧） |

新規プロジェクトを追加する場合は、新しいシートを追加し、凡例シートへのリンクを貼る。

### 5.2 各シートの列構成

| 列  | 項目名      | 内容                               |
| --- | ----------- | ---------------------------------- |
| A   | #           | 通番（#1, #2, …）                  |
| B   | 記入日      | テスター記入日                     |
| C   | テスト内容  | テストした操作・シナリオ           |
| D   | 宛先/記入者 | テスターの名前                     |
| E   | 優先度      | 大 / 中 / 小                       |
| F   | 概要        | 不具合・改善要望の一言まとめ       |
| G   | 詳細        | 再現手順・期待動作・実際の動作など |
| H   | ステータス  | 未対応 / 対応中 / 済               |
| I   | 改修日      | 開発者が修正した日付               |
| J   | 改修内容    | 何をどう修正したか                 |
| K   | 備考        | その他コメント                     |

### 5.3 優先度の定義

| 優先度 | 基準                                                             |
| ------ | ---------------------------------------------------------------- |
| 大     | アプリが使えない・クラッシュする・データが壊れる等、致命的な問題 |
| 中     | 機能は動くが意図と異なる動作・UI の重大な問題                    |
| 小     | 軽微な表示崩れ・誤字・改善要望                                   |

### 5.4 テスターへの連絡ルール

テスターとの連絡は LINE または Slack で行う。

**連絡前に必ず守ること（ルール 5-7）**:

> シートへの記入と、LINE・Slack への送信は、実行前に必ず内容を依頼者（発注者）に提示して確認を取ること。テスターへの連絡は対外的な発信であり、送信は取り消せない。

連絡内容のテンプレート:

```
件名: [アプリ名] テスト依頼

〇〇さん

お疲れ様です。
[アプリ名] の以下の機能についてテストをお願いします。

【テスト内容】
- [具体的なテストシナリオを記載]

【期間】
[開始日] 〜 [終了日]

不具合・改善要望はスプレッドシートの「[シート名]」シートに記入してください。
https://docs.google.com/spreadsheets/d/1YfWo9xvDaRscJ3kHET-LUNd-SV1yvKilEeP5ZZO-Szc/edit

よろしくお願いします。
```

### 5.5 開発者側のワークフロー

1. スプレッドシートの「未対応」行を定期確認する
2. 対応着手時にステータスを「対応中」に変更する
3. 修正完了後、「ステータス: 済」「改修日」「改修内容」を記入する
4. 優先度「大」の問題は即日対応を目標とする
5. 対応完了後、必要に応じてテスターへ再確認依頼を行う（ルール 5-7 に従い発注者に確認を取ってから送信）

### 5.6 テスト配布方法

| プラットフォーム | 配布方法                                                             |
| ---------------- | -------------------------------------------------------------------- |
| iOS              | TestFlight（内部テスター登録が必要）                                 |
| Android          | Google Play Console クローズドテスト（メールアドレスでテスター招待） |

**TestFlight（iOS）の流れ**:
1. `eas build --platform ios` でビルド
2. `eas submit --platform ios --latest` で App Store Connect に提出
3. App Store Connect の TestFlight ページで内部テスターに通知
4. テスターは TestFlight アプリからインストール・アップデート

**Google Play クローズドテスト（Android）の流れ**:
1. `eas build --platform android` で AAB をビルド
2. Play Console の「テスト > クローズドテスト」で App Bundle をアップロード
3. テスターのメールアドレスをリスト登録し、「リリース」する
4. テスターはメールのリンクか Google Play から参加・インストール

**内部テスターへのアップデート連絡テンプレート**:

```
[アプリ名] が更新されました（v[バージョン番号]）。

【主な変更点】
- [変更点1]
- [変更点2]

[TestFlight / Google Play] からアップデートをお願いします。
```

## 付録: 開発・リリースチェックリスト

### リリース前確認

- [ ] バージョン番号を更新した（`app.json` の `version` / `buildNumber` / `versionCode`）
- [ ] API 側のバージョン情報環境変数を更新した（`APP_VERSION_IOS` / `APP_VERSION_ANDROID`）
- [ ] TestFlight / Play Console に最新ビルドを提出した
- [ ] テスターへの案内文を発注者に確認・承認をもらった
- [ ] テスターへ連絡した
- [ ] スプレッドシートの「未対応」が 0 件になっていることを確認した（または意図的に持ち越した理由を記録した）

### 機能追加・変更後の通知

| 対象                             | 通知要否           |
| -------------------------------- | ------------------ |
| ユーザーが使う画面・フローの追加 | ✅ プッシュ通知必須 |
